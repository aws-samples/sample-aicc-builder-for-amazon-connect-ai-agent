AICC Builder 3.0 · validation pipeline

Where the deterministic gates sit, asset by asset

An LLM writes each asset once; everything after that is code. Each row is one asset family, each column one stage: the interview completeness gate, generation, the save- and merge-time gates inside the generator, the cross-asset consistency gate, the reviewer whose blocking set is computed in code, and packaging. Details: docs/validation-pipeline.md.

Per asset

Each generator runs its own deterministic gates right after the model answers: lint + normalize for the Classic assets, canonicalize → runtime contract → schema → D9 in a retry loop for an ACXD flow. Most rewrite the asset in place and report what changed.

Across assets

validate_parameter_consistency joins the stored assets against the OperationSpec (D1–D8, IAM, sample data) and, for ACXD, the application against OpenAPI, CloudFormation, the Contact Flow and the FAQ (D9). It never writes; it is read once by the review and, for ACXD, again by the packager.

Reviewer

The reviewer's ❌/⚠️ are advisory. The blocking set is computed in code from the deterministic gates with stable ids, so a fix loop has a fixed exit condition; fixes are patch-only and start with the deterministic repair tools. Only the ACXD download is refused on open findings.
